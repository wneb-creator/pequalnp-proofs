# Exact rational row-certificate calibration

This archive contains an independently reviewed certificate pipeline and two restricted calibration systems. It does not prove or refute L-gct-231.

The four-variable rowzero system reaches a unit ideal in 0.034 seconds. Exact replay checks all 170 output identities; its useful certificate has 63 polynomial steps. `F4TraceRowzero.lean` is the 71,633-byte complex-typed Lean emission. Its corrected compile passed in58.933seconds with exit0 and peakprocessgroupRSS5,994,936KiB; the two earlier failed versions and complete error logs are included. Their final constant equation defaulted to Nat before the explicit complex-type correction.

The nine-variable star-support system reaches a unit ideal in 3.131 seconds with 32 critical pairs per batch. Both the strict-format parser and SymPy parser replay all 2,492 output identities and produce byte-identical complete certificates. The archive keeps the complete operation trace and a compact dependency slice, rather than the redundant 47 MB indented full certificate. The slice has 26 input equations and 698 polynomial consequences. The independent review in `review/` checks each parent identity without importing either replay implementation, regenerates all 31 chart equations via a different permanent algorithm, and verifies that source rescalings preserve the zero set.

The full 18-variable path chart has no verdict. Batch32 failed under its 2 GiB address-space limit after 15.646 seconds; batch4 timed out after 120.078 seconds under 4 GiB. Complete process stdout/stderr and reproduction parameters are included. The unfinished auxiliary row traces are retained in scratch only, with sizes and SHA256 hashes in `metadata.json`; they support no mathematical conclusion.

## Reproduction

The source is based on OpenF4 commit `7155c6ec4e5f776e0e12202716dc7da58469e77b` from `https://github.com/nauotit/openf4`, under GPL-3.0 (COPYING included). The baseline requires the supplied `openf4-local-build.patch` and the two configuration defines in `config.h`. Place that source in a sibling `openf4/` directory, then run `make_trace_overlay.py`; it creates an isolated `trace-openf4/` tree and the supplied adapter. It never modifies the baseline.

Build with:

```sh
g++ -std=c++11 -O2 -I trace-openf4 openf4_qq_trace.cpp -lgmpxx -lgmp -o openf4_qq_trace
```

The adapter accepts `INPUT TRACE [BATCH_LIMIT]`. `run_f4_trace.py` adds wall-time and address-space limits and preserves complete stdout/stderr. The default batch limit is 32; the known support trace was generated by the earlier fixed-32 version with the same row hooks and arithmetic. Every logged consequence is independently checked, so the solver's basis verdict is not trusted.

For example:

```sh
python3 run_f4_trace.py qq-star-support.in support --seconds 120 --memory-mib 2048 --batch 32
python3 replay_f4_trace.py qq-star-support.in support.trace support.certificate.json
```

`emit_f4_trace_lean.py` selects the proved unit's dependency closure and emits only explicit polynomial consequences using `linear_combination`. It refuses output above 512 KiB. Direct expansion of the support certificate is too large; no support Lean theorem is claimed. The rowzero calibration fits the size budget. No compiled binaries are archived.
